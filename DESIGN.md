# gomisat design notes

**Goal: exploit systematic structural similarity across reliability WMC queries.**

gomisat is not an attempt to build a competitive general-purpose SAT solver. It is
a research platform for *weighted model counting over sequences of related
formulas*, where the sequences come from reliability evaluation of multi-state
systems and fault trees. The SAT core exists to be good enough, and to be fully
under our control, so that decomposition, caching and cross-query reuse can be
designed across the whole stack rather than on top of a black box.

## Why not just use an existing solver

Improving pure SAT performance carries little research novelty, and the field is
crowded: kissat and CaDiCaL in C, splr in Rust, gini and gophersat in Go. Any of
them will out-solve this code on SAT competition benchmarks, and that is fine.

The gap this project addresses is elsewhere. Counting-side engines
(sharpSAT, GANAK, d4, sharpSAT-TD) are all C/C++ and are built for *single*
queries. Cross-instance reuse for #SAT has only recently been studied
(Bartal, Fried and Lagniez, arXiv:2605.00671, May 2026: a persistent component
cache retained across solver calls, plus branching heuristics adapted to the
incremental setting), and that work targets argumentation and soft-core problems,
not reliability. gophersat has a `CountModels`, but it is plain model enumeration,
not decomposition with a component cache, and it is unweighted.

So: a necessary-and-sufficient CDCL core, and novelty on the counting and
reliability side.

## The query sequences we care about

A reliability evaluation produces a sequence of counting queries
`(F_1, w_1), ..., (F_T, w_T)`. Two cases have to be separated, because they call
for different machinery:

**Weights only (`F` fixed, `w_t` varies).** Time-dependent reliability `R(t)`
evaluated at many time points. Here compile-once-evaluate-many wins: build a
d-DNNF or BDD once and re-evaluate the weights. d4 already does exactly this, as
do BDD packages. **This is a baseline to compare against, not a target.**

**Structure varies (`F_{t+1} = F_t + Δ_t`).** Threshold changes in a multi-state
system, a different `k` in `k`-out-of-`n`, component configuration changes,
phased-mission phase transitions, design alternatives, successive queries
conditioned on failure or repair states. This is the target.

The bet: in the reliability setting `Δ_t` is *generated by a known rule*, not
arbitrary. A cache entry `C = (V_C, F_C, #(F_C))` need not be invalidated because
the formula changed somewhere; it can be kept whenever the change does not touch
its variables, e.g. `Δ_t ∩ V_C = ∅`, and the dependency structure that decides
this is known from the reliability model rather than recovered from the CNF.
That is the step beyond a generic persistent component cache, and it is the
intended contribution.

For weighted counting there is a second separation to exploit: if a cache entry
records the logical structure and the weight evaluation separately,
`C = (V_C, F_C, W_C)`, then a query that keeps the structure and changes only the
weights re-evaluates instead of re-searching.

Experimental picture this sets up:

| query sequence | expected winner |
| --- | --- |
| logic fixed, weights vary | d-DNNF / BDD compile-once |
| logic changes substantially | fresh WMC |
| logic changes locally and systematically | gomisat cross-query reuse |

External comparisons: BDD-based (`JuliaSylvan.jl`, `bdd-parallel`), d4, GANAK,
and gomisat's own fresh-WMC mode.

## Phases

| phase | content | status |
| --- | --- | --- |
| 0 | public API for repeated queries, regression and benchmark infrastructure | done |
| 1 | minimum-modern CDCL: LBD + tiered learnt-clause management, restart policy, vivification and basic inprocessing | next |
| 2 | component decomposition + component cache | |
| 3 | weighted model counting | |
| 4 | repeated-query API + persistent cache across calls | |
| 5 | **reliability-aware selective cache reuse** — the research contribution | |
| 6 | evaluation against BDD-based counting, d4, GANAK and fresh WMC | |

Phase 1 stops deliberately. Chronological backtracking, a clause arena
allocator, proof logging and bounded variable elimination are all worth having,
but none of them is on the path to phase 5; they get picked up only when a
measurement says they block progress.

## Invariants

Every phase is validated against the properties in
`pkg/gomisat/regression_test.go`, which is the reason phase 0 comes before any
change to the search:

1. **status** — the answer matches the known status of every SATLIB instance
   (2185 instances; `GOMISAT_FULL=1 make test-full`).
2. **model** — an LTrue answer comes with an assignment satisfying every clause.
3. **oracle** — status and model agree with exhaustive enumeration on small
   random instances, with and without assumptions.
4. **reuse** — a reused solver answers exactly as a freshly built one, and an
   UNSAT core is a subset of the assumptions that is sufficient on its own.

Invariant 4 is the one the later phases will keep breaking, and invariant 3 will
become the oracle for counting as well: exhaustive enumeration gives the exact
weighted count on small instances.

## Defects found while building phase 0

All four were dormant in the sense that the ordinary DIMACS-in, answer-out path
mostly hid them.

- `VarHeap.RemoveMin` reset the index of the removed variable to `0` instead of
  `-1` when the heap held a single element, so `InHeap` reported it as present
  and `Insert` ignored it from then on. The variable could never be chosen as a
  decision again, and the search then answers LTrue with that variable
  unassigned, i.e. reports an assignment that does not satisfy the formula. The
  C++ original guards the move with `if (heap.size() > 1)`.

  How far this reaches is worth recording, because the mechanism does not depend
  on assumptions. It was found by the reused-solver invariant. With a freshly
  built solver, however, the original code answers all 2185 SATLIB instances
  correctly *and* produces a valid model for every satisfiable one, so
  single-query solving is not demonstrably affected on this corpus. Treat it as
  established for repeated queries and unquantified for single queries.
- The assumption placement loop in `search` used a bare `break` inside a
  `switch`, which in Go leaves the switch and not the loop, so an unassigned
  assumption made it spin forever. Reached only once assumptions are actually
  usable from outside.
- `solve` never returned to the root level, so a second call on the same solver
  started from a trail left inside a decision level.
- `Clause.Subsumes` had an inverted size guard, returned on the first negated
  literal instead of checking the remaining ones, and `findLit` reported a
  negated occurrence as an exact one. Unused until subsumption and vivification
  arrive in phase 1.

## Known gaps

- **The corpus is too easy to measure search changes.** All 2185 instances are
  solved in under 0.8 s in total, the slowest taking 27 ms. It validates
  correctness, not performance; phase 1 needs harder instances (SAT competition
  benchmarks) before LBD or restart changes can be judged.
- No clause arena allocator: clauses are individually allocated and the watcher
  lists keep pointers. Not a problem at the current scale, but it is the reason
  GC pressure will show up once learnt clauses reach the hundreds of thousands.
- No proof logging (DRAT/LRAT), no bounded variable elimination, no
  `SimpSolver` equivalent.
- Clause addition after the first solve is untested.
