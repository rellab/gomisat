# Working on gomisat

[USAGE.md](USAGE.md) is the user's guide. [../DESIGN.md](../DESIGN.md) is the record
of what was built, in what order, and what every measurement said -- including the
predictions that turned out wrong, which are the useful part. This page is how to
work on the code without breaking what has been established.

## The one rule

**Measure before changing, and measure again after.** Every default in this module
is a measurement, and the settings each of them beat are still selectable so the
measurement can be repeated. That is not ceremony: the profile has disagreed with
the prediction at almost every step of this project, and the two changes that looked
most obviously like optimisations both had to be measured twice before they helped.

Two corollaries that cost real time to learn.

**Never write an expected value by hand.** Enumerate it. A hand-computed expectation
in a count-preservation test recorded a defective encoding as correct and the correct
one as broken, and the same mistake then went into an example. Expected values in
the tests come from enumeration or a closed form, never from arithmetic in a comment.

**Reproducibility first, then speed.** An encoding that changed size by three
quarters between runs was measured twice before anyone noticed; the numbers from
before the fix were comparing arms that had been encoded differently. If a
measurement surprises you, check that the thing you are measuring is the same thing
twice.

## Running things

```console
$ make check         # go vet and the regression suite on a sample of each family
$ make test-full     # the same suite over all 2185 committed instances
$ make fmt           # gofmt the tree

$ make corpus        # fetch the larger corpus, once (about 99 MB, outside the tree)
$ make corpus-sweep  # record bench/corpus-t10.csv, checking every decided answer
$ make corpus-compare # re-run and compare; an answer that changed fails the target
$ make bench-suite   # the same over the committed instances
$ make bench         # micro-benchmarks with a CPU profile in pprof/
```

`GOMISAT_FULL=1 go test ./...` is what `test-full` does; the suite samples each
instance family by default so that it stays fast.

`corpus/expected.tsv` is ground truth from CaDiCaL, regenerated by
`make corpus-expected`, which needs `pip3 install --user python-sat`. It exists
because the answers implied by the corpus directory names were wrong about one
instance, and a corpus labelled from the same assumptions as the solver checks
nothing.

## The invariants

`pkg/gomisat/regression_test.go` holds four properties. A change that breaks one of
them is wrong, however good it looks.

1. **status** -- the answer matches the known status of every SATLIB instance.
2. **model** -- an `LTrue` answer comes with an assignment satisfying every clause.
3. **oracle** -- status and model agree with exhaustive enumeration on small random
   instances, with and without assumptions.
4. **reuse** -- a reused solver answers exactly as a freshly built one, and an UNSAT
   core is a subset of the assumptions that is sufficient on its own.

The counter has its own three, in `count_test.go`, `weighted_test.go` and the two
model packages: agreement with enumeration in every combination of decomposition,
caching and branching order; agreement between the weighted counter with unit
weights and the unweighted one, which are deliberately separate implementations of
the same recursion; and agreement with the closed forms of reliability theory.

`pkg/csp` adds one more that is easy to lose: the number of models of an encoding
must equal the number of solutions of the model. See *Encodings* below.

## The shape of the code

| | |
| --- | --- |
| `pkg/gomisat/solver.go` | CDCL search, propagation, conflict analysis |
| `pkg/gomisat/clause.go` | the clause arena: metadata and literals in two flat arrays |
| `pkg/gomisat/lbd.go` | literal block distance, clause tiers, the reduction schedule |
| `pkg/gomisat/restart.go` | restart policies |
| `pkg/gomisat/branch.go` | the counter's branching order, from an elimination order |
| `pkg/gomisat/count.go` | model counting: decomposition and caching |
| `pkg/gomisat/weighted.go` | weighted counting, and where reliability comes out |
| `pkg/gomisat/study.go` | a sequence of queries sharing the cache |
| `pkg/gomisat/incremental.go` | model, core and assumption accessors |
| `pkg/reliability` | structure functions of coherent systems |
| `pkg/csp` | finite-domain constraint problems |

Some things are deliberately not optimised. **The unweighted counter is the
reference implementation** the weighted one is checked against, and keeping it
simple is worth more than making it fast: it still keys its cache by the full
component description, allocates components from the heap and sorts with
`sort.Slice`. Leave it that way unless the reason it exists has changed.

## Two hazards in the counter

**Clause references and the arena.** A `CRef` is an index into the metadata array,
not an offset into the literal store, which is why compacting the store needs no
reference rewriting. Deletion is lazy: a clause is flagged, propagation drops the
watchers it meets, and `collectGarbage` sweeps the rest *before* any metadata slot is
handed out again. Recycling a slot while a watcher still points at it would silently
turn that watcher into a watcher of a different clause. The structural invariants in
`simplify_test.go` check this after a solve and across a sequence of queries.

**Slices into the arenas.** `arena.Lits(c)` aliases the literal store and the
counter's component arenas hand out slices with a stack discipline. A slice must not
be held across an `alloc` or a `compact`, and the component arenas must be marked on
entry to a subtree and released on the way out. Propagation writes through `Lits`
deliberately, when it reorders watched literals.

## Encodings, and the mistake that keeps being available

Counting demands more of an encoding than solving does: an auxiliary variable
introduced for a subformula must be **determined** by the original variables. If it
can take either value while the subformula holds, the same solution is counted more
than once, and nothing complains.

The polarity-optimised conversion that satisfiability normally uses gives each
auxiliary only the implication it needs, and it is wrong for counting -- but not
always, which is the trap. Two mutually exclusive branches of a disjunction come out
right; two overlapping ones are inflated by 1.3; three by 1.65. So the first case
tried passes.

Every encoding in this module therefore has a count-preservation test against
enumeration, and `pkg/csp` keeps the wrong conversion available and *requires* the
test to show it failing somewhere, so that the reason for the default cannot quietly
stop being true.

The same applies to weights. The order encoding of a multi-state component cannot
carry a state distribution on independent literal weights, and the one-hot encoding
requires weight one on the false indicators rather than the complement. Charging the
complements turned a reliability of 0.99999 into 0.0023. That is why the weights
belong to the model, set by `SetProbability` or `SetStateProbabilities`, each of which
knows the rule its own encoding needs.

## Adding a policy or a heuristic

Follow what the existing ones do:

1. Put it behind an option in `SolverOptions` or `CountOptions`, with the current
   behaviour still reachable.
2. Expose it on `cmd/gomibench` (or `cmd/gomisat`) so that both arms can be run
   without rebuilding.
3. Measure on the corpus, or on `cmd/gomiencode` if it concerns encodings. Report
   answers changed, decisions, and time separately -- decisions and time have parted
   company more than once, most recently at 140 components where an encoding took
   twice the decisions and was still faster.
4. Record the numbers in DESIGN.md, including what you expected. The record of wrong
   predictions is the most reused part of that document.
5. Keep the losing arm switchable and tested, so the next person can repeat the
   measurement rather than trusting it.

## What is known to be missing

DESIGN.md has the current list under *Known gaps*. The standing ones: nothing evicts
from the component cache; `Var` and `Lit` are 64-bit where 32 would halve the watch
lists and the literal store; there is no proof logging; vivification and inprocessing
are postponed because the present corpus cannot measure them; and clause addition
after the first solve is untested.
